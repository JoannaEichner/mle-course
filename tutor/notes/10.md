## What the learner should own after this module

- A regression tree picks the split that most reduces the sum of squared deviations; a leaf predicts a mean; trees need no scaling, find interactions, and do not extrapolate.
- Random forest: deep independent trees on bootstrap samples, averaged, to reduce variance. Boosting: shallow trees in sequence, each fitting the residuals (negative gradient), scaled by the learning rate, to reduce bias; the number of trees is chosen by early stopping.
- LightGBM settings that matter: rounds + early stopping, learning rate, leaves and minimum leaf size, objective (L2, Poisson, Tweedie), native categories with stable codes, monotone constraints.
- kNN as a contrast: no training, costly prediction, needs scaling.
- Gain importance says what the trees used, not what the feature is worth; SHAP decomposes one forecast; neither is causal.
- Direct versus recursive multi-step forecasting and their trade-off.

## Tasks

### 10.1 `sum_of_squares`, `best_split`

- Thresholds at data values instead of midpoints: the check expects midpoints.
- Candidate thresholds between equal values: a split that separates equal feature values is impossible. The check has repeated values.
- Ties: the docstring says the lowest threshold; `np.argmax` on gains returns the first maximum, which is the lowest if the candidates are sorted ascending.
- O(n²) loop: passes the check (small data), takes a long time on 100k rows in the notebook. Ask them to time it, then point at cumulative sums.
- No `ValueError` for a constant feature.

### 10.2 `LightGBMForecaster`

- Categories coded with `astype("category")` separately in fit and predict: the same store gets different codes when predict sees a different set. The check predicts one store's rows alone and compares.
- Early stopping without keeping the best iteration: `predict` must use `rounds_used`.
- Monotone constraints in the wrong order (dict order instead of feature order).
- `valid` rows including stockout days while training excludes them: allowed, but ask which days the stopping criterion should look at.

### 10.3 `importance`, `contributions`

- `importance_type="split"` (count) instead of gain: the check expects shares of gain summing to 1, sorted.
- Forgetting `num_iteration=self.rounds_used` in `pred_contrib`: contributions sum to a different forecast than `predict`.

### 10.4 forecasting

- Not erasing outcome columns of the future rows in `stack_future`: the check passes real values and expects NaN.
- `forecast_direct` returning forecasts in panel order instead of `future`'s order and index.
- Recursive loop that builds features once before the loop: the lag 1 of day 2 is then NaN instead of day 1's forecast. The check's model "yesterday + 1" exposes it.
- Writing forecasts into a copy (chained indexing) so the panel never changes. `panel.loc[today, TARGET] = ...`.

## The questions at the end of the lab

Discuss, do not grade.

1. **Ids with the largest importance.** The model learned a per-series level, not "understanding". A new product arrives as a missing category and without sales history; its forecast rests on calendar, price and whatever the model does with NaN. Cold start needs other information (category hierarchy, similar products).
2. **Monotone constraint barely changes WAPE.** It guarantees sensible behaviour in situations that rarely occur in validation (a new, deeper discount), it protects against learning noise, and it makes the model defensible to users. Small cost, real protection.
3. **What gain importance does not say.** What would happen without the feature. Example: two strongly correlated history features; the model uses one, dropping it changes little because the other takes over. Or a feature used a lot on training noise.
4. **Why lag 1 helps less than expected.** From day 2 on, "yesterday" is a forecast, not an observation, so it carries the model's own error and no new information; daily fresh-food sales are noisy, so yesterday's single value adds little beyond the 7-day and 28-day means.
