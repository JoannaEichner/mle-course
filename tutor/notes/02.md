## What the learner should own after this module

- A signature is a contract: keyword-only arguments after `*`, `*args` and `**kwargs` for pass-through, no mutable defaults.
- Functions are values: passed to `sorted(key=...)`, returned from factories, stored in a dict.
- A closure remembers variables, not values; functions made in a loop see the last value.
- A decorator is `f = deco(f)`. The wrapper passes `*args, **kwargs`, uses `functools.wraps`, and stacked decorators apply bottom-up.
- A decorator factory validates its parameter when the decorator is applied, not when the function runs.
- Type hints do nothing at runtime; `mypy` reads them. Parameters wide (`Sequence`, `Mapping`), results narrow. Narrowing applies to names, not to repeated expressions like `row[key]`.
- `ruff format`, `ruff check` and `mypy` pass before a commit (K1, K9). Docstrings describe behaviour (K2).

Classes are module 03. If the object style in the lecture raises questions, answer briefly and point there.

## Tasks

### 02.1 Typed module

- Typing `values: list[float | None]` for `demand_stats`. mypy accepts it; it is not wrong. Ask whether the function needs to change the list, and what a caller with a tuple would hear from mypy.
- `top_series` with `if row[key] is not None` inside the comprehension: mypy reports `List[float | None]`. Do not give the walrus. Ask: "Which variable does mypy know is not None?" The lecture's quiz q3 covers it.
- `read_series(path: Path)` only: fine for the check, but the notebook passes a `Path` and the check passes a `Path`. Ask what happens when someone passes a string from a config file.
- Generator return type: `Generator[tuple[...], None, None]` also works. `Iterator[...]` is the simpler choice; both are fine.
- `Stats` values: `months` is an int, stored in `dict[str, float | None]`. mypy accepts int where float is expected. If they ask, explain that rule directly.
- Adding `# type: ignore` to silence mypy. Ask what error it hides and whether a reviewer would accept it (K1 is blocking).
- Forgetting `ruff format`: the check says so and gives the command.

### 02.2 `timed`

- No `functools.wraps`: the check names it.
- Printing only after a successful call. The check raises inside the function and expects the line anyway. Lead to `try/finally`, not `except`.
- `time.time()` instead of `time.perf_counter()`. Passes. Mention that `perf_counter` is the clock meant for intervals; do not insist.
- Catching the exception inside the wrapper and returning `None`: the check reports that the exception vanished. Ask who would notice a silently swallowed error in a nightly job.
- Wrong format (`took 0.1s`, milliseconds). The check shows the expected shape.
- mypy on the wrapper: `*args: P.args, **kwargs: P.kwargs` and `-> R`. If mypy complains about `Callable[P, R]` being returned, the wrapper is probably missing annotations.

### 02.3 `requires_history`

- Validating `min_months` inside `wrapper`: the error appears only when the statistic runs. The check calls `requires_history(0)` without applying it. Ask when each of the three functions runs.
- Counting known months with truthiness (`if v`): zeros drop out. The check's second series has a zero on purpose.
- Returning `statistic` instead of `wrapper`, or `decorator(statistic)` inside itself: confusion about levels. Ask them to write, for `@requires_history(12)`, which call receives 12, which receives the function, which receives the values.

### 02.4 Registry

- Decorator order on `cv2`: `@requires_history(12)` above `@register("cv2")` registers the unguarded function. The check calls `STATISTICS["cv2"]` on 11 months and says to look at the order. Ask them to rewrite the stack as nested calls.
- 02.4b: copying `demand_stats` logic for `months` with `len([...])` is fine; returning an `int` where `float | None` is declared passes mypy.
- Registering the same name twice after editing the file: with `%autoreload 2` the module is re-executed, `STATISTICS = {}` is rebound first, so no error. Registering from the notebook (02.6) and running the cell twice does raise. That is the point of question 1 in 02.6.
- `cv2` with sample variance (`n - 1`): gives 0.133 instead of 0.111 on the check's series. The task says population variance.
- `summarise` that silently skips unknown names. Ask what a typo in a config would then produce.
- Mutating `STATISTICS` in `summarise`. Rare; if it happens, point at module 01's rule about not changing inputs.

### 02.5 `at_least`, `select`

- `stats[key]` in the test: `KeyError` on a series without that key. The check passes `{}`.
- `select(stats, tests)` with a list instead of `*tests`: the call in the check passes two tests positionally, so it fails with a `TypeError`.
- Building the tests in a loop with `lambda` in the notebook: they all use the last threshold. If you see it, ask them to print each test's result for one value. The lecture's p5 is the same trap.

## The questions in 02.6

Discuss, do not grade.

1. **Registering `peak` twice.** The second run raises `ValueError`: the name is taken. Good, because two statistics under one name would silently replace each other, and which one wins would depend on execution order.
2. **Registry versus one function.** Adding to `demand_stats` means editing a tested function and its test; the registry means adding one new function. What the registry does not give for free: a guaranteed order of results (it is insertion order, which depends on import order), and it is global state: whoever imports the module can add to it, and tests must clean up after themselves, as the check does.
