# Module 17: working in someone else's code

Code: `shelfwise/`. Tickets: `shelfwise/tickets/T1.md` to `T6.md`. Checks: `uv run course check 17` (each starts as failing; that is expected).

## What the learner should own after this module

- Reading before changing: run the program, find the entry point (`cli.py`), follow one number from input to output.
- Reproducing the symptom with data before touching code.
- A failing test that captures the cause, then the fix, then the test passes. One ticket, one branch, one pull request.
- Leaving code better only where the ticket touches it. A ticket is not a licence to reformat the whole package.
- Profiling before optimising.

## How to guide

The learner does not know where the defects are, and must not learn it from you. Your material is the ticket, the learner's own measurements and generic debugging moves. Do not name files or functions unless the learner has already pointed at them.

Good generic questions, in rough order:

1. "Where does the number in the ticket come from? Which function writes that column?"
2. "Can you get the same number for one product by hand, from the invoice lines?"
3. "At which step do your number and the program's number first differ?"
4. "What would a test that fails for exactly this reason look like?"

For each ticket:

- **T1 (totals):** push them to reproduce 97 111 for 85123A from raw invoice lines themselves, then compare with `clean(...)` output line by line for a few cancellation invoices. The insight they need: quantities on "C" invoices are already negative.
- **T2 (new metric):** an ordinary feature. Ask where the validation rows with forecasts exist (`train_and_validate` returns them) and where categories come from (`build_catalogue`). If they join the catalogue and the row count grows, they have found defect 4 on their own: help them notice it, as a separate fix.
- **T3 (new feature):** a four-part change: setting, feature, tests, docs. The check also reads the README. Ask them to report validation WAPE with and without the feature, whatever it is.
- **T4 (optimistic validation):** the question that cracks it is "what does the model know, at training time, about the validation weeks?" Suggest the experiment: multiply sales in the validation weeks by 100 and see whether the forecast for the first validation week changes. It should not.
- **T5 (flaky test):** ask them to run the test pretending it is 5 January (`freezegun.freeze_time`). The fix is to pass the time in, not to change the expected string.
- **T6 (slow report):** ask for a measurement per step first. Once the loop is found, ask what one `merge` could replace it.

Defects without a ticket, which the learner may find: duplicated catalogue rows (report longer than the number of products), zero prices for products without recent sales, weeks labelled with Sundays. Treat a find as a win and ask for a separate pull request.

## Quiz bank

- "You changed one line and three unrelated tests fail. What do you do before anything else?"
- "What is the difference between reproducing a bug and reading about it?"
- "Why does a test that fails only in January do more damage than no test?"
- "The validation score went down after your fix of T4. Is that good news or bad news?"
