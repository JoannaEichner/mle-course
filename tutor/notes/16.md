## What the learner should own after this module

- Image versus container; layers and the build cache; dependencies installed before the code is copied.
- A production image: two stages, `uv sync --locked`, `--no-editable`, `libgomp1` for LightGBM, a non-root user, no data or secrets inside, data mounted at run time, settings through environment variables.
- CI on a clean machine for every pull request, the same tools as local checks (G3), `--locked` so the lock and `pyproject.toml` cannot drift silently.
- pre-commit as the fast, local, skippable twin of CI, using the tools from the project's lock.
- Review: blocking findings with a place, a rule and a concrete failing input; non-blocking suggestions separated; one thing done well; questions rather than rewrites.

## Facts worth having at hand

- The reference Dockerfile pins uv 0.12.21 from `ghcr.io/astral-sh/uv`; the workflow uses `actions/checkout@v7` and `astral-sh/setup-uv@v9` (v10 exists too). All exist as of 2026-10.
- The author could not run `docker build` (the Docker daemon is off on the author's machine) and the workflow has not run on GitHub. The steps inside the Dockerfile were rehearsed on a clean Ubuntu 24.04 without Docker. If a learner hits a build error, treat it as possibly the course's bug: read the log with them and report it.
- On Windows, Docker Desktop needs WSL integration switched on for the Ubuntu distribution; `docker` inside WSL fails with "command not found" or "Cannot connect to the Docker daemon" otherwise.
- `docker run -v "$PWD":/work` writes `artifacts/` into the repository as the container's user. On WSL and most Linux setups the host user and `app` are both uid 1000; if not, the files belong to another uid. Point at `--user "$(id -u):$(id -g)"`.
- The check for 16.1 reads the Dockerfile text; it cannot build it.

## Tickets

### 16.1 Dockerfile

- One stage with `pip install`: works, big, unpinned. Ask how they would get the exact versions of `uv.lock`.
- `uv sync` without `--locked`, or `--frozen`: `--frozen` installs from the lock without checking it matches `pyproject.toml`. Ask what happens when someone edits `pyproject.toml` and forgets `uv lock`.
- `COPY . .` before installing dependencies: every code change reinstalls all packages. Ask them to time two builds after a one-line change.
- Editable install in the final stage: the package links to `/app/src`, which is not in the final image. Symptom: `ModuleNotFoundError: freshcast` at run time.
- Missing `libgomp1`: `OSError: libgomp.so.1` when LightGBM is imported.
- Running as root: the check reports it. Ask what an attacker who takes over the process could then do inside the container.
- Data copied into the image or `.dockerignore` missing `data`: the build context uploads gigabytes and the check reports it.

### 16.2 CI

- Triggers only on `push`: pull requests from forks are not checked. The check asks for `pull_request`.
- `uv sync` without `--locked`.
- A missing step (format check is the one most often forgotten).
- `pip install` of ruff at a different version than the lock: CI and local runs then disagree about formatting.

### 16.3 pre-commit

- ruff from the `ruff-pre-commit` repository at its own pinned version, which drifts from the lock. Acceptable, but ask how they keep the two versions equal; the local hooks through `uv run` avoid the question.
- mypy with filenames passed: mypy then checks single files without the project's config. `pass_filenames: false`.
- Forgetting `uv run pre-commit install`: the config does nothing until the hook is installed.

### 16.4 Review of `pull-request-42.diff`

What a complete review finds. Line numbers refer to the new file `promo.py` in the diff.

Blocking:

1. `promo.py:6-11`, G4: hard-coded access keys and an internal endpoint, and a client created at import time (importing the module talks to a server). The keys must also be revoked: they are in the history now.
2. `promo.py:16-17`, C2: `sales_in_stock` of the same day, an outcome column. The registry entry in `catalog.py` even declares it as a requirement.
3. `promo.py:18-21`, C1: `rolling` without `groupby` by series: windows cross series boundaries.
4. `promo.py:18-21`, C2 again: the window ends today (no shift), so even with legal inputs it would include the forecast day.
5. `promo.py:15-17`, D4: the function writes three columns into the caller's frame.
6. `promo.py:27-30`, K4: `except Exception: pass` hides a failed upload; the function then prints success anyway.
7. K1 and K2: no type hints, no docstrings on public functions.
8. T1: no tests for three public functions.
9. `catalog.py`: `promo` is used but never imported, so the module fails at import (ruff F821, CI red, G3).

Non-blocking (a good review picks up to five):

- `promo.py:22`, D3: `fillna(0)` claims "no uplift" for series without promo days; and a zero base gives `inf`, which `fillna` does not touch.
- `promo.py:15`, K5: the magic threshold 0.9.
- NaN discounts (the zero-discount marker from module 07) count as "not on promo" silently.
- `min_periods=1`: a one-day window passes as a weekly mean.
- `uplift_by_store`, K7: a loop over stores where `groupby` does it; it also calls the mutating function on slices, which raises pandas warnings.
- `print` in the package (K8).
- The feature is registered but not added to a feature list, so no model uses it: ask whether that was intended.

Something positive is hard to find; a fair one: the idea (promotion response per product) is sensible, and the author put the feature in the registry rather than computing it ad hoc in a notebook.

The verdict is "do poprawy". A learner who finds fewer than six blocking issues should go through the blocking rules one by one again rather than read the code "for problems".
