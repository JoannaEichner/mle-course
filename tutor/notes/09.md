Lecture: `lectures/09-features/index.html`. Lab: `labs/09-features/`. Code: `src/freshcast/features/` (`calendar.py`, `lags.py`, `demand.py`, `encoding.py`, `build.py`; `catalog.py` is given). The notebook order is 09.1, 09.2, 09.5, 09.3, 09.4, because the experiments need the feature table.

## What the learner should own after this module

- Every feature is known at forecast time for the whole horizon: lag ≥ horizon, windows ending `horizon` days back (C2). The code enforces it with `check_horizon`.
- Calendar: day of week, cyclical encoding for linear models, holidays from a calendar that knows the future, days to the next holiday.
- Category encodings and when each fits; target encoding leaks twice: fitted on validation (C4), and in-sample on the training rows themselves.
- Transformers that learn from data are fitted inside a `Pipeline` on training rows only.
- Features as pure functions registered with their requirements; a topological order computes them; training and forecasting call the same code.
- Censored demand: sales on stockout days are below demand. Correction versus exclusion, decided by measurement. A simulation checks a method only under its own assumptions.

## The experiments and the questions in 09.6

Discuss, do not grade.

1. **What leaked in "training + validation".** Each validation row's encoding includes its own target (one of about 12 rows in its series × weekday group), so the model partly sees the answer on validation. C4: fitting only on training rows. Validation picked the worst variant; test exposed it.
2. **Why the honest encoding still hurts.** In training, each row's code includes its own target (one of about 11 rows), so the code looks more predictive in training than it is on new rows, and the model over-trusts it. Out-of-fold encoding, heavier smoothing, or leaving categories to LightGBM (module 10) avoid it.
3. **Simulation versus reality.** The simulation drew stockout start times at random on ordinary days. Real stockouts happen on high-demand days (module 07: sales peak at two to three stockout hours), whose hourly shape differs, so the profile misjudges the missing share. A simulation validates a method only within its assumptions.
4. **Registry and the pipeline.** The same functions compute features for history and for the future week; a new feature is one registered function; the dependency order is computed, not remembered. Training/serving skew becomes much less likely.
