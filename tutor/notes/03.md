## What the learner should own after this module

- `self` is the object a method was called on; state is set in `__init__`, class-level attributes are shared.
- `@dataclass` writes `__init__`, `__repr__`, `__eq__` from annotated fields; `frozen=True` blocks assignment and adds `__hash__`, but a list field can still be mutated.
- Invariants live in `__post_init__`: an invalid object is never created.
- `@property` for values derived from fields; `@classmethod` for alternative constructors, returning `cls(...)` and typed `Self`.
- A base class does the shared work and calls a method subclasses implement; `ABC` + `@abstractmethod` makes a missing implementation fail at construction.
- `Protocol` describes what an object can do; `mypy` checks it structurally.
- `StrEnum` for a closed set of string values; `match` for branching on the shape of data.
- When a class adds nothing over a function.

### 03.2 `DemandType`, `classify`

## The questions in 03.6

Discuss, do not grade.

1. **Zero wins MAE.** Most holdout months are zero; the median of each series' future is zero, and MAE rewards forecasting the median. The warehouse needs total volume to order stock; the zero forecast orders nothing. A metric for model choice must not reward systematic under-forecasting; module 05 introduces WAPE and bias. Do not explain module 05 in detail here.
2. **Rankings per type.** They differ: naive is best on intermittent, the 12-month average on lumpy. Rare, irregular demand is better estimated from a longer history. The general point: an average over all series can hide opposite results in subgroups.
3. **`classify` as function or method.** For a function: it depends only on two numbers, is easy to test and reuse elsewhere (for example on daily data later). For a method or property: `series.demand_type` reads well and keeps the knowledge next to `adi` and `cv2`. Both are defensible; the reasoning is what matters.
