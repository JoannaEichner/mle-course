    Docker i CI

    Kod, który działa u Ciebie, musi działać też na serwerze, w CI i u kolegi. Kontener zamyka aplikację z całym jej środowiskiem, a ciągła integracja sprawdza każdą zmianę, zanim ktokolwiek zacznie ją czytać. Trzecia część tego modułu dotyczy ludzi: jak robić review, które pomaga, a nie tylko wyraża opinię.

    • Czas: około 45 minut
    • Wymagane: moduły 04, 14 i 15
    • Potem: lab 16 i punkt kontrolny 3, około 5 godzin

    Po tym wykładzie będziesz umiał:

    • napisać Dockerfile dla aplikacji z uv: warstwy, cache, dwa etapy, zwykły użytkownik,
    • uruchomić kontener z zamontowanymi danymi i ustawieniami ze środowiska,
    • skonfigurować GitHub Actions i pre-commit tak, żeby sprawdzały to samo,
    • zrobić review według standardu: uwagi blokujące z konkretem, reszta jako sugestie.

    Obraz i kontener

    Obraz to zapis systemu plików z aplikacją i wszystkim, czego ona potrzebuje: system, Python, pakiety, kod. Kontener to uruchomiony obraz: proces odizolowany od reszty maszyny, z własnym widokiem plików. Z jednego obrazu uruchomisz wiele kontenerów, na laptopie, w CI i w chmurze, i wszystkie zobaczą to samo środowisko.

    Obraz buduje się z Dockerfile, instrukcja po instrukcji. Każda instrukcja tworzy warstwę, a Docker zapamiętuje warstwy. Jeśli ani instrukcja, ani pliki, które kopiuje, się nie zmieniły, warstwa bierze się z cache. Dlatego kolejność ma znaczenie:

    # 1. Dependencies: rebuilt only when uv.lock or pyproject.toml change
RUN --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project

# 2. The code: rebuilt on every change in src/, but reuses layer 1
COPY src ./src
RUN uv sync --locked --no-editable
    W Dockerfile najpierw jest COPY . ., potem uv sync --locked. Zmieniasz jedną linię w src/freshcast/cli.py. Co się przebuduje?
    • Tylko warstwa z kodem.Warstwą z kodem jest tu COPY . ., a po niej jest instalacja wszystkich zależności.
    • Wszystko od COPY . ., łącznie z instalacją wszystkich pakietów.Tak. Zmiana dowolnego pliku unieważnia warstwę COPY i każdą po niej. Zależności instaluje się przed skopiowaniem kodu.
    • Nic, Docker wykryje, że zależności się nie zmieniły.Docker nie wie, co robi uv sync. Widzi tylko, że warstwa przed nim się zmieniła.

    Dobre praktyki

    • dwa etapy: w pierwszym instalujesz wszystko, do drugiego kopiujesz tylko gotowe środowisko. uv, cache i narzędzia budowania nie jadą do produkcji,
    • zablokowane wersje: uv sync --locked instaluje dokładnie to, co w uv.lock, albo kończy się błędem,
    • zwykły użytkownik: proces w kontenerze nie potrzebuje roota. Jeśli ktoś przejmie aplikację, nie przejmie z nią uprawnień administratora,
    • bez danych i sekretów w obrazie: dane, ustawienia i artefakty montuje się przy uruchomieniu (-v), klucze przekazuje w zmiennych środowiskowych (-e). Obraz można pokazać każdemu,
    • .dockerignore: bez niego do kontekstu budowania trafia .git, .venv i gigabajty danych.
    docker build -t freshcast .
docker run --rm -v "$PWD":/work -e FRESHCAST_MODEL__ROUNDS=200 \
    freshcast train --config configs/standard.yaml
    Kolega kopiuje do obrazu katalog data/ "żeby kontener miał dane pod ręką". Co jest nie tak?
    • Nic, to przyspiesza uruchomienie.Obraz rośnie o gigabajty, a każda nowa wersja danych wymaga nowego obrazu.
    • Obraz rośnie, wiąże kod z jedną wersją danych i może wynieść dane poza firmę razem z obrazem.Tak. Obraz to kod i środowisko. Dane montuje się przy uruchomieniu albo czyta z bucketu (moduł 15).
    • Docker nie pozwala kopiować danych.Pozwala. To zły pomysł, a nie zabronione polecenie.

    Ciągła integracja

    CI uruchamia sprawdzenia na czystej maszynie przy każdej zmianie. Czysta maszyna to ważne słowo: nie ma tam Twojego .venv, danych na dysku ani pakietu zainstalowanego ręcznie tydzień temu. Jeśli CI przechodzi, projekt da się postawić od zera.

    name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  checks:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v9
        with:
          enable-cache: true
      - run: uv sync --locked
      - run: uv run ruff check .
      - run: uv run ruff format --check .
      - run: uv run mypy
      - run: uv run pytest

    pre-commit uruchamia te same narzędzia przed commitem, na zmienionych plikach. Po co oba? pre-commit daje odpowiedź w sekundę, ale da się go pominąć (--no-verify) albo nie zainstalować. CI jest ostatnią linią obrony i nie da się go obejść. Oba biorą narzędzia z tego samego uv.lock, więc nie spierają się o wersję ruff.

    CI na Twoim pull requeście jest czerwone na kroku pytest, a lokalnie testy przechodzą. Co sprawdzasz najpierw?
    • Czy da się wyłączyć ten krok w CI.Czerwone CI mówi, że projekt nie działa na czystej maszynie. Wyłączenie kroku ukrywa problem.
    • Log kroku: który test i dlaczego. Częste przyczyny to plik obecny tylko u Ciebie, dane, sieć albo data w teście.Tak. Test zależny od lokalnego stanu łamie T4. CI właśnie to wykrył.
    • Czy ktoś inny zepsuł main.Możliwe, ale log powie to szybciej niż zgadywanie.

    Review

    Review to nie ocena autora, tylko sprawdzenie zmiany, zanim trafi do wspólnego kodu. Dobre review:

    • rozdziela uwagi blokujące od reszty. Blokujące to złamane reguły z oznaczeniem "blokuje", błąd poprawności albo wyciek. Reszta to sugestie, które autor może przyjąć albo nie,
    • jest konkretne: miejsce, reguła i przykład danych, na których kod zadziała źle. "Ten rolling miesza serie" jest słabe. "Na panelu dwóch serii pierwsza średnia serii B obejmuje ostatnie 6 dni serii A, promo.py:18, C1" jest mocne,
    • pyta, zamiast przepisywać. Kod poprawia autor, a recenzent pokazuje problem,
    • widzi też dobre rzeczy. Jedno konkretne zdanie o tym, co jest zrobione dobrze, pomaga powtórzyć to następnym razem.
    Które uwagi do pull requesta są blokujące według standardu kursu? Zaznacz wszystkie.
    • Klucz dostępu do S3 wpisany w kod.Tak. G4: sekrety nie trafiają do repozytorium. Klucz trzeba też unieważnić, bo historia gita go pamięta.
    • Cecha liczona z sales_in_stock tego samego dnia.Tak. C2: cecha musi być znana w chwili prognozy.
    • Zmienna nazwana df2.Słaba nazwa to dobra sugestia, ale nie blokada.
    • except Exception: pass w funkcji zapisującej wynik.Tak. K4: połknięty wyjątek ukrywa awarię, a funkcja udaje sukces.
    • Nowa funkcja publiczna bez testu.Tak. T1 blokuje.

    Gdy review dostajesz, pamiętaj, że uwagi dotyczą kodu, a nie Ciebie. Pytanie recenzenta to często sygnał, że kod nie mówi sam za siebie. Czasem lepiej dopisać komentarz albo zmienić nazwę, niż wyjaśniać w wątku.

    Ćwiczenia

    Przegląd Dockerfile

    Napisz dockerfile_problems(text): lista problemów w treści Dockerfile. Szukaj trzech: brak USER (kontener jako root), uv sync bez --locked, kopiowanie katalogu data. Zwracaj krótkie nazwy: "root", "unlocked", "data", w tej kolejności.

    Sprawdzenie workflow

    Napisz missing_checks(workflow): dla workflow wczytanego do słownika (tak jak robi yaml.safe_load) zwróć posortowaną listę narzędzi spośród mypy, pytest, ruff, których żaden krok run nie uruchamia.
