    Klasy

    Klasa łączy dane z regułami, które te dane muszą spełniać, i z operacjami na nich. Dobrze użyta sprawia, że niepoprawny obiekt w ogóle nie powstaje. Źle użyta zamienia trzy linijki funkcji w trzydzieści linijek ceremonii.

    • Czas: około 60 minut
    • Wymagane: moduły 01 i 02
    • Potem: lab 03, około 6 godzin

    Po tym wykładzie będziesz umiał:

    • napisać klasę z __init__, atrybutami i metodami i wiedzieć, czym jest self,
    • zastąpić ręcznie pisaną klasę danych przez @dataclass, także zamrożony,
    • używać właściwości i metod klasy,
    • zbudować rodzinę klas ze wspólną umową: dziedziczenie, ABC, Protocol,
    • nazwać skończony zbiór wartości przez StrEnum i rozgałęziać kod przez match,
    • ocenić, kiedy klasa jest zbędna.

    Klasa, obiekt, self

    Klasa to przepis na obiekty. Obiekt (instancja) ma własne atrybuty, a metody klasy działają na nich:

    class Stock:
    def __init__(self, part: str, units: int) -> None:
        self.part = part
        self.units = units

    def take(self, count: int) -> None:
        if count > self.units:
            raise ValueError(f"Only {self.units} units of {self.part} left.")
        self.units -= count


oil = Stock("olej", 5)
oil.take(2)

    oil.take(2) to w istocie Stock.take(oil, 2). self to po prostu pierwszy argument metody: obiekt, na którym ją wywołano. __init__ ustawia atrybuty nowego obiektu. Nie tworzy go i niczego nie zwraca.

    Atrybut ustawiony przez self.x = ... należy do obiektu. Atrybut zapisany w ciele klasy należy do klasy i jest wspólny dla wszystkich obiektów:

    class Basket:
    items = []

    def add(self, item):
        self.items.append(item)

a = Basket()
b = Basket()
a.add("olej")
print(b.items)
    • []Tak by było, gdyby każdy koszyk miał własną listę. Tu lista powstała raz, przy definicji klasy.
    • ['olej']Tak. items to atrybut klasy, jedna lista dla wszystkich koszyków. To ta sama pułapka co domyślny argument [] z modułu 01.
    • AttributeErrorObiekt, który nie ma własnego atrybutu, szuka go w klasie. b.items znajduje listę klasy.

    Stan obiektu ustawiaj w __init__. W ciele klasy trzymaj tylko stałe.

    dataclass

    Wiele klas to po prostu nazwane zestawy pól. Pisanie dla nich __init__, __repr__ i __eq__ ręcznie jest nudne i łatwo o błąd. Dekorator @dataclass robi to z listy pól:

    from dataclasses import dataclass

@dataclass
class Part:
    name: str
    price: float

print(Part("filtr", 20.0) == Part("filtr", 20.0), Part("filtr", 20.0))
    • False <__main__.Part object at 0x...>Tak zachowuje się zwykła klasa: porównuje tożsamość i wypisuje adres. @dataclass dopisuje porównanie pól i czytelny opis.
    • True Part(name='filtr', price=20.0)Tak. Dwa obiekty z równymi polami są równe, a print pokazuje nazwę klasy i pola.
    • True filtr 20.0Wygenerowany __repr__ pokazuje też nazwę klasy i nazwy pól.

    Adnotacje typów w ciele klasy są tu obowiązkowe: z nich @dataclass wie, jakie są pola. Pole z wartością domyślną będącą listą zapisujesz jako field(default_factory=list), bo zwykłe = [] byłoby wspólne dla wszystkich obiektów (dataclass na to nie pozwoli).

    Walidacja i zamrożenie

    Własne sprawdzenia dopisujesz w __post_init__, które dataclass wywołuje na końcu wygenerowanego __init__. Obiekt z błędnymi danymi wtedy nie powstaje.

    @dataclass(frozen=True) blokuje przypisanie do pól po utworzeniu. Taki obiekt jest bezpieczny do przekazywania: nikt go po drodze nie zmieni. Dostaje też __hash__, więc może być kluczem słownika albo elementem zbioru. Zamrożenie dotyczy jednak tylko pól:

    from dataclasses import dataclass

@dataclass(frozen=True)
class Series:
    name: str
    values: list

s = Series("A", [1, 2])
s.values.append(3)
print(s.values)
    • FrozenInstanceErrorTen błąd pojawia się przy przypisaniu s.values = .... append nie przypisuje pola, tylko zmienia listę, na którą pole wskazuje.
    • [1, 2]Lista jest zmienna niezależnie od tego, kto na nią wskazuje.
    • [1, 2, 3]Tak. Zamrożony obiekt nie pozwala podmienić listy, ale samą listę da się zmienić. Dlatego w labie values to krotka.
    Reguła

    Obiekt z danymi, które nie powinny się zmieniać, to @dataclass(frozen=True) z polami niezmiennymi: str, liczby, tuple, date. Warunki, które dane muszą spełniać, sprawdza __post_init__.

    Właściwości i metody klasy

    Właściwość (@property) to metoda, którą czytasz jak atrybut, bez nawiasów. Nadaje się do wartości wyliczanych z pól: series.adi zamiast osobnego pola, które ktoś musiałby aktualizować.

    class Stock:
    def __init__(self, units):
        self.units = units

    @property
    def empty(self):
        return self.units == 0

s = Stock(3)
s.units = 0
print(s.empty)
    • TrueTak. Właściwość liczy się przy każdym odczycie, więc widzi aktualne units.
    • FalseTak by było, gdyby empty było polem ustawionym w __init__. Właściwość nie pamięta starej wartości.
    • <bound method Stock.empty ...>Tak wyglądałaby zwykła metoda odczytana bez nawiasów. @property wywołuje ją za Ciebie.

    Metoda klasy (@classmethod) dostaje zamiast obiektu samą klasę, nazywaną cls. Typowe użycie to alternatywny konstruktor, czyli obiekt z innego formatu danych:

    @dataclass(frozen=True)
class DemandSeries:
    name: str
    start: date
    values: tuple[float | None, ...]

    @classmethod
    def from_record(cls, record: tuple[str, str, Sequence[float | None]]) -> Self:
        name, start, values = record
        return cls(name, date.fromisoformat(start), tuple(values))

    Dlaczego cls(...), a nie DemandSeries(...)? Bo klasa pochodna, która odziedziczy from_record, dostanie obiekt swojej klasy, a nie bazowej. Stąd też typ wyniku Self.

    @staticmethod nie dostaje ani obiektu, ani klasy. To zwykła funkcja w przestrzeni nazw klasy. Zwykle lepiej zrobić z niej funkcję modułu.

    Dziedziczenie i umowy

    Klasa pochodna dziedziczy metody klasy bazowej i może je nadpisać. Metoda bazowa, która wywołuje self.cos(), wywoła wersję klasy pochodnej:

    class Forecaster:
    def name(self):
        return "base"

    def describe(self):
        return f"model {self.name()}"

class Naive(Forecaster):
    def name(self):
        return "naive"

print(Naive().describe())
    • model basedescribe jest zdefiniowane w klasie bazowej, ale self to obiekt Naive, więc self.name() szuka najpierw w Naive.
    • model naiveTak. Na tym opiera się wzorzec z labu: klasa bazowa robi wspólną pracę i woła metodę, którą każda klasa pochodna implementuje po swojemu.
    • AttributeErrorNaive dziedziczy describe po Forecaster.

    super() daje dostęp do wersji metody z klasy bazowej. Klasa pochodna z własnym __init__ woła super().__init__(), żeby klasa bazowa ustawiła swoje atrybuty.

    Klasa abstrakcyjna

    Klasa bazowa, której obiektów nie chcesz tworzyć, dziedziczy po ABC. Metody, które klasy pochodne muszą napisać, oznaczasz @abstractmethod. Python nie pozwoli utworzyć obiektu klasy, która którejś z nich nie ma:

    from abc import ABC, abstractmethod

class Model(ABC):
    @abstractmethod
    def predict(self): ...

class Broken(Model):
    def fit(self):
        return self

Broken()
    • Nic się nie dziejeTak byłoby bez ABC. Wtedy błąd wyszedłby dopiero przy wywołaniu predict, może na produkcji.
    • TypeErrorTak. Broken nie ma predict, więc jest dalej abstrakcyjna. Błąd wychodzi przy tworzeniu obiektu, najwcześniej jak się da.
    • NotImplementedErrorTen wyjątek rzuca się ręcznie w metodzie, której nie napisano. ABC działa wcześniej, przy tworzeniu obiektu.

    W labie LocalForecaster ma dwie publiczne metody, fit i predict, które sprawdzają argumenty, i jedną abstrakcyjną, _forecast, która liczy. Każdy model pisze tylko _forecast, a walidacja jest w jednym miejscu. Podkreślnik na początku nazwy mówi: to szczegół implementacji, z zewnątrz tego nie wołaj.

    Protocol

    Dziedziczenie mówi: "jestem rodzajem X". Czasem potrzebujesz tylko: "umiem zrobić to i to". Funkcja oceniająca modele nie musi wiedzieć, po czym model dziedziczy. Wystarczy jej, że ma fit i predict. To opisuje Protocol:

    class Forecaster(Protocol):
    def fit(self, history: Sequence[float]) -> Self: ...
    def predict(self, horizon: int) -> list[float]: ...


def evaluate(make_model: Callable[[], Forecaster], ...) -> float: ...

    Każda klasa z pasującymi metodami spełnia Forecaster, także klasa z cudzej biblioteki, która nigdy o nim nie słyszała. mypy sprawdza to, porównując metody. Python w czasie działania niczego nie sprawdza: to znane z Pythona "duck typing", tylko z kontrolą typów.

    Chcesz, żeby evaluate przyjmowało też model z zewnętrznej biblioteki, która ma metody fit i predict, ale jej klas nie możesz zmienić. Jaki typ dajesz parametrowi?
    • Klasę bazową LocalForecaster.Klasa z biblioteki po niej nie dziedziczy, więc mypy ją odrzuci.
    • Protocol z metodami fit i predict.Tak. Protocol sprawdza kształt obiektu, a nie jego pochodzenie.
    • Any.Zadziała, ale mypy przestanie cokolwiek sprawdzać, także literówkę w predcit.

    StrEnum i match

    Typ popytu to jedna z kilku wartości: "smooth", "lumpy" i tak dalej. Trzymanie ich jako luźnych napisów kończy się literówką "lumpy " w jednym miejscu kodu. StrEnum daje nazwany, zamknięty zbiór wartości, które nadal są napisami:

    from enum import StrEnum

class Kind(StrEnum):
    SMOOTH = "smooth"
    LUMPY = "lumpy"

print(Kind("lumpy") is Kind.LUMPY, Kind.SMOOTH == "smooth", f"{Kind.LUMPY}")
    • True True Kind.LUMPYTak wypisałby zwykły Enum. StrEnum w napisie jest swoją wartością.
    • True True lumpyTak. Kind("lumpy") zwraca istniejącego członka, porównanie z napisem działa, a w f-stringu członek to jego wartość. Dlatego StrEnum dobrze się zapisuje do plików i kolumn.
    • False True lumpyCzłonkowie wyliczenia istnieją w jednym egzemplarzu. Kind("lumpy") zwraca właśnie jego.

    match dopasowuje wartość do kolejnych wzorców i wykonuje pierwszy pasujący. Wzorzec może rozpakować krotkę, sprawdzić stałą i mieć strażnika if:

    def describe(record):
    match record:
        case (name, None):
            return f"{name}: brak"
        case (name, 0):
            return f"{name}: zero"
        case (name, value) if value > 10:
            return f"{name}: dużo"
        case _:
            return "inne"

print(describe(("T1", 0.0)), describe(("T2", 12)), describe(["T3", None]))
    • inne T2: dużo inneStałe we wzorcu porównuje się przez ==, a 0 == 0.0. Wzorzec krotki pasuje też do listy.
    • T1: zero T2: dużo T3: brakTak. 0.0 pasuje do 0, strażnik przepuszcza 12, a wzorzec sekwencji pasuje i do krotki, i do listy.
    • T1: zero T2: dużo inneWzorzec (name, None) dopasowuje każdą dwuelementową sekwencję, także listę.

    match nie jest szybszym if. Opłaca się, gdy rozgałęziasz według kształtu danych: kilku pól naraz, typu, długości. Dla jednego porównania if jest czytelniejszy.

    Kiedy nie pisać klasy

    Klasa ma sens, gdy daje coś, czego funkcja nie da:

    • niezmiennik: dane, które muszą spełniać warunki, a obiekt pilnuje ich od utworzenia,
    • stan, który zmienia się w czasie i trzeba go chronić, jak nauczony model,
    • kilka wymiennych implementacji jednej umowy, jak modele prognozy.

    Sygnały, że klasa jest zbędna:

    • ma dwie metody, z czego jedna to __init__. To funkcja z dodatkowymi krokami,
    • ma same metody statyczne. To moduł,
    • ma nazwę z końcówką Manager, Helper, Utils. Nikt nie wie, za co odpowiada.
    Kolega napisał class ZeroShareCalculator z __init__(self, values) i jedną metodą calculate(self). Co proponujesz w review?
    • Dodać @dataclass.Skróci kod, ale dalej będzie to klasa, która nic nie daje ponad funkcję.
    • Funkcję zero_share(values).Tak. Obiekt żyje tylko po to, żeby wywołać jedną metodę. Funkcja mówi to samo krócej i łatwiej ją przetestować.
    • Klasę abstrakcyjną Calculator, na przyszłość.Abstrakcja bez drugiej implementacji to koszt bez zysku. Dodasz ją, gdy pojawi się drugi przypadek.
